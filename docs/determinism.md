# 确定性契约

**目标程序的行为必须是模糊输入的纯函数。** 除测试接口外的一切数据交互，
由测试配置固定。

这条约束在 Magma 和 OSS-Fuzz harness 里都不成立，是 MemVulBench 的差异化点之一，
也是符号执行 / 记录重放类工作（SymAFL、SEDBT）能否用这个测试集的硬前提。

与准入闸门同一条哲学：**确定性是测出来的，不是声称的。**

## 1. 分级

不确定性的代价随观测粒度急剧上升，所以分级承诺，而不是一刀切。

| 级 | 保证 | 谁需要 |
|---|---|---|
| **D1** | 崩溃/不崩溃稳定 | PoC 复现、sanitizer 评测 |
| **D2** | sanitizer 报告（类型 + 栈）逐条一致 | 崩溃归因、去重研究 |
| **D3** | **覆盖率位图逐位一致** | 所有 coverage-guided fuzzer |
| **D3p** | 持久模式下，结果与同进程内的执行顺序无关 | 用 persistent mode 的 fuzzer |
| **D4** | 完整地址/指令轨迹一致（含堆地址） | 符号执行、DBT、记录重放 |

**已定：D1–D4 全部为硬性准入门槛，达不到的切片不收。** 含堆地址逐字节一致。

这条决定的代价要预先说清楚：多线程目标基本出局；重度依赖时间/随机的目标要靠
包装层救回来；能活下来的候选组会明显少于 62 个。这个折损率本身要测出来，
作为选片的输入。

一个必须先厘清的区分：**我们承诺的是"目标本身不含任何阻碍 D4 的因素"，
而不是"某个具体二进制满足 D4"。** 被测工具会用自己的插桩重建目标，
布局必然与我们的参考构建不同。D4 是目标（源码 + harness + 运行契约）的属性，
在我们的参考构建上验证；工具自己的构建能否保持 D4，由协议要求工具自证。

D3p 单列的理由：它不是"同一输入跑两次结果一样"，而是"输入 x 的结果不依赖于
同进程里先跑过什么"。这一条被违反得极其普遍（harness 不清理全局状态），
而它会让 persistent mode 的 fuzzer 和 fork 模式的 fuzzer 得到系统性不同的结果——
直接破坏可比性。没有任何现有测试集检查这一条。

## 2. 不确定性来源与对策

### 2.1 地址布局

| 来源 | 对策 |
|---|---|
| ASLR | `personality(ADDR_NO_RANDOMIZE)`；容器里需 `--security-opt seccomp=unconfined`（默认 seccomp 会挡掉，实测踩过） |
| PIE 随机基址 | `-no-pie` 固定装载地址 |
| ASan 影子区/分配器 | 关 ASLR 后确定；但必须关掉 `allocator_release_to_os_interval_ms` |

**注意**：ARVO/OSS-Fuzz 默认的 `ASAN_OPTIONS` 里带
`allocator_release_to_os_interval_ms=500`，这是**基于时间**的行为，直接破坏 D4。
复现参考指纹时要用它，做确定性构建时必须覆盖掉。这两套选项要分开管理。

### 2.2 时间、随机、身份

`time` / `clock_gettime` / `gettimeofday` / `rdtsc`、`rand` / `getrandom` /
`/dev/urandom` / `RDRAND`、`getpid` / `gettid` / `gethostname` / `getuid`。

目标与外界的数据交互几乎全部经由外部函数调用，而这些外部函数不在测试分析范围内，
所以把它们换成我们自己的确定性包装层是正当的。四种落地方式：

| 方式 | 评价 |
|---|---|
| `LD_PRELOAD` 注入 | **占用了 LD_PRELOAD 这个位置**，而被测 fuzzer 经常要用它 |
| 直接编辑源码 | 侵入目标源码，破坏"漏洞体与历史逐字节等价"的不变式 |
| `-Wl,--wrap=sym` | 链接期，只作用于跨编译单元的未定义符号，同 TU 内的调用拦不到 |
| **强制包含头文件** `-include memvul_det.h` | 编译期宏替换调用点，**一行源码都不用改** |

**主用强制包含头文件**：它实现了源码级替换的效果，却不产生任何源码 diff，
因此与保真不变式完全相容；OSS-Fuzz 目标全部从源码静态构建，覆盖面接近全集；
DBT 类工具重建后也照样看到已确定化的代码。
`--wrap` 作为兜底，处理函数指针间接调用和预编译库里的调用。

**不要包装内存分配函数。** `malloc` / `free` / `memcpy` 恰恰是内存漏洞的作用面，
换掉它们等于改变漏洞本身。所幸也不需要：关掉 ASLR 之后，ASan 的分配器
（固定影子基址 + 固定尺寸类区域）和 glibc malloc 都已经是确定的，
堆地址逐字节一致可以不靠包装拿到。

### 2.2.1 完备性论证

"我们想到了哪些不确定函数"是开放式枚举，再多测试也无法证真。
完备性必须靠**按信息通道穷举**来论证，测试只用来核验前提是否成立。

> **闭合性主张**：一个用户态进程能够获得的、不由其输入决定的信息，
> 只能来自以下 6 类通道。逐类封死，则程序状态演化是输入的确定函数。

| # | 通道 | 封堵手段 | 核验方式 |
|---|---|---|---|
| 1 | 系统调用 | 限制在允许集（读输入 / 内存映射 / 退出），结果由配置固定 | seccomp 审计模式，越界即判失败 |
| 2 | **vDSO** | 见下 | 越过内核，seccomp 看不见 |
| 3 | 不确定指令 `rdtsc` / `cpuid` / `rdrand` | `prctl(PR_SET_TSC, PR_TSC_SIGSEGV)`；`arch_prctl(ARCH_SET_CPUID, 0)`；编译期锁 ISA 排除 rdrand | 陷阱计数应为 0 或走虚拟化路径 |
| 4 | exec 时的初始进程状态 | 关 ASLR；固定 argv/envp 内容**与总长度**；`AT_RANDOM` 见下 | 比对初始栈镜像 |
| 5 | 未初始化内存读 | 新页由内核清零故确定；复用内存在其余通道封死后亦确定 | MSan 审计定位 |
| 6 | 线程调度 | 强制单线程，做不到则拒收 | 线程创建系统调用应为 0 |

两个纯靠测试极难暴露的缺口：

**vDSO 绕过 seccomp。** `clock_gettime` / `gettimeofday` / `time` / `getcpu`
在 x86-64 上由 vDSO 在用户态直接服务，**根本不产生系统调用**。
只做 seccomp 审计会给出"无越界调用"的假阴性。
必须靠通道 1 之外的手段处理：强制包含头文件的宏替换在编译期就改掉了调用点，
天然覆盖 vDSO 路径——这也是它优于 `--wrap` 和 seccomp 的地方。

**`AT_RANDOM` 不受 ASLR 开关影响。** 内核在 auxv 里放 16 字节随机数供栈保护
和指针混淆使用，`setarch -R` **不会**把它固定下来。后果是栈金丝雀值和
被 `PTR_MANGLE` 混淆过的指针在内存中的字节形态每次都不同。
这不影响地址一致，但影响内存内容一致。对策是目标一律
`-fno-stack-protector`；若 D4 要求扩展到内存内容一致，则需要额外处理。

### 2.3 环境与文件系统

- `getenv`：wrap 成只从固定表返回。注意 sanitizer 运行时在 `main` 之前就读环境。
- **环境变量的总字节数会移动初始栈指针** —— 读未初始化栈内存的目标，
  行为会随环境大小变化。这一条特别隐蔽，而且意味着
  **离线 oracle 重放的环境必须与战役环境逐字节一致**，否则重放结果不等于工具当时看到的。
  对策：把环境填充到固定长度。
- 文件系统：只读、固定的工作根目录；`mkstemp` / `tmpnam` 依赖 PID 和随机数，要 wrap。
- `LC_ALL`、`TZ` 固定。

### 2.4 线程

任何多线程都引入调度不确定性。优先强制单线程构建；做不到的目标直接拒收，
并把拒收原因记账。

### 2.5 CPU 特性分发（跨机器可比性）

运行期按 CPU 能力分发到 SIMD 路径的代码，在不同机器上走不同分支。
后果不只是覆盖率不可比：**AVX2 路径里的漏洞在没有 AVX2 的机器上根本不触发。**

对一个要被多个实验室引用的测试集，这是可比性的硬伤。对策是编译期锁定基线 ISA，
或者 wrap 掉能力探测函数。这一条必须写进发布契约。

### 2.6 持久模式的状态泄漏（D3p）

harness 在两次迭代之间不清理全局状态 —— 静态缓存、单例、未复位的解析器上下文、
上一次的 `errno`、没释放的内存。这类问题在一次性执行下完全看不出来。

对策属于 harness 纪律，可能需要我们改 harness（改 harness 不违反漏洞体等价性，
因为 harness 不是漏洞体）。

## 3. 强制手段分层

| 层 | 内容 | 是否影响漏洞体等价性 |
|---|---|---|
| L1 构建期 | `-no-pie`、锁定 ISA、单线程、`-Wl,--wrap=...` | 否（不改源码） |
| L2 运行契约 | 固定环境表与长度、`setarch -R`、钉死 `ASAN_OPTIONS`、只读固定 CWD | 否 |
| L3 harness 纪律 | 迭代间复位全局状态、禁止读输入以外的任何东西、禁止写文件系统 | 否（harness 不是漏洞体） |

三层都不碰漏洞体，与"函数级历史回溯"的保真不变式相容。

## 4. 抽样核验（辅助手段）

完备性由 §2.2.1 的通道论证承担。测试的作用**不是证真**，而是核验论证的前提
在具体目标上确实成立——比如宏替换是否真的覆盖了所有调用点、
是否存在函数指针间接调用绕过了替换。因此抽样即可，不必海量。

核验时必须**故意制造扰动**：在同一环境里重复十次，恰好会掩盖所有环境依赖。

```
输入集   = 全部 PoC + 种子语料的一个样本
扰动维度 = PID、环境变量长度、CWD、系统时间、执行顺序、（可选）不同机器
重复     = 每输入 N 次

比对 D1  退出状态
比对 D2  归一化后的 sanitizer 报告
比对 D3  覆盖率位图（需插桩构建）
比对 D3p 随机打乱顺序后，每输入的结果是否与单独执行一致
比对 D4  完整地址轨迹
```

切片在哪一级全等，就承诺到哪一级。不达 D3/D3p 的切片不发布。

## 5. 约束怎么落地

**已定：靠协议，不靠技术强制。** 我们发布确定性检查器，评测协议写明
**实际被评测的那个二进制必须通过 D1–D4 检查，否则结果不作数。**

理由是我们控制不了别人的构建流程，与其设计一套能被绕过的强制机制，
不如把举证责任交给使用者，并提供一个谁都能跑的裁判程序。
这也顺带解决了"工具用 DBT 重建目标"这类我们根本无法拦截的情形。

2. D4 硬门槛会淘汰掉多少候选组？需要在 62 个候选上跑一遍审计才知道。
3. 环境变量填充到固定长度之后，战役环境与离线重放环境还剩哪些差异？
4. 被测工具自己的插桩（覆盖率位图、DBT）会不会引入新的不确定源？
   这属于工具自证的范围，但检查器要能给出可读的失败定位。
