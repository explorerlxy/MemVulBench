# 构建方法论：纯考古

如何得到一批高密度、崩溃可验证的 C/C++ 内存漏洞目标，且构建成本可控。

本文取代此前的两版方案：**修复回退**（已被实测否定，§1）与**文件级时间 pin**
（未被否定，但成本与收益不匹配，降级为可选增量，§9）。

---

## 0. 定位

MemVulBench 不是一个要独立发表的 benchmark artifact，而是**支撑 fuzzing 技术研究的评测平台**。
唯一的成功判据是：能不能可信地支撑"本方法比 baseline 发现更多漏洞"这个主张。

这个定位决定了全部取舍。凡是为了"benchmark 本身作为科学工件站得住"而付出的成本
（难度标定、密度失真量化、未知漏洞普查、确定性契约），一律不做，理由与代价记在 §10。

---

## 1. 已被实测否定的：修复回退

assimp 端到端试点（2026-09-08，`assimp_fuzzer`，基线 `3c253ca3`）：

| 环节 | 结果 |
|---|---|
| 修复补丁回退到基线 | 12/12 干净应用 |
| 回退后 PoC 真正复现 | **3/14（21%）** |
| 同一基线上天然潜伏（不打任何补丁） | **6/6（100%）** |

**补丁能否应用完全不能预测漏洞能否重现。** 漏洞不是补丁的逆运算——它是某个文件在某一时刻的
整体形态，依赖当时的缓冲区声明方式、当时还没被重构掉的调用点、当时的校验顺序。
`git revert <fix>` 只把其中一行改回去，产出的是历史上从未存在过的混合体。
这正是 Magma 沉默漏洞的机制，而且证明了它不是"手工移植不够仔细"的问题。

**但第三行才是真正的发现**：不做任何改动时，成功率是 100%。
整套方法论就建立在这一行上。

---

## 2. 唯一构建操作：选一个 commit

```
target = 上游某个 commit C，未经任何修改
bugs(target) = 在 C 上构建后 PoC 实际开火、且指纹匹配的那批漏洞
```

没有 pin，没有补丁，没有一行手写代码。由此白拿三条性质：

- **保真平凡满足**。目标就是上游某次提交的原貌，`git checkout` 即可复验，
  不需要 manifest、不需要 `mosaic_ratio`、不需要论证"这个程序历史上存不存在"。
- **负对照不需要**。漏洞本来就在树上，不存在"崩溃是不是我的改动造成的"这个问题。
  PoC 开火 + 指纹匹配就是完整证据。
- **构建配方直接复用**。ARVO 镜像里的 `compile` 对同项目的老 commit 通常仍然适用，
  不需要为每个目标写构建脚本。

代价是单目标密度受历史支配，拿不到 26，大概率落在 6–12。§3 说明为什么这不重要。

---

## 3. 放弃单目标高密度

要密度是为了解决 ARVO"一次战役只产出 1 个二元结果、统计功效不足"的问题。
但这个问题的解不在密度的绝对值上：

**从 1 涨到 8 已经解决了 90%，从 8 涨到 26 是边际收益递减区，工程量却是十倍**
（认领集扩张阶梯、冲突图、最大独立集、保真 manifest、存活窗口实测）。

总漏洞数改由**项目数量**提供：

```
12 个目标 × 8–10 个天然潜伏漏洞 ≈ 100+ 个已验证可观测漏洞
```

对照 Magma：138 条 canary，实测只有 45 条（32.6%）在真实测试场景下可观测。
**纯考古路线的总可观测漏洞数是 Magma 的两倍以上，而构建成本接近于零。**

本质是**用算力换工程量**。多目标意味着多跑几轮战役，算力可以排队；
单目标高密度意味着多写几千行求解器和验证器，时间不能排队。

---

## 4. 找基线：批量修复日

assimp 数据里的关键观测：**8 个漏洞的修复日期同为 2021-10-29**，加上 11-12 的一个共 9 个。
也就是说 2021-10-28 那个快照上，这 9 个漏洞零改动天然共存。

这不是巧合，而是 OSS-Fuzz 的结构性产物：

> 项目接入 OSS-Fuzz 的初期会被灌进一大批漏洞报告，维护者按批次集中修复。
> **每一波批量修复的前一天，就是天然密度的局部峰值。**

推论：候选基线可以**纯靠 ARVO 元数据算出来，零构建成本**。对每个 (项目, harness)
把 fix commit 的日期做直方图，取修复最密集的若干波，各取其前一个 commit 作为候选。
待实测的基线数量因此从"按月扫 30 个"降到"5 个左右"。

这一步同时完成**项目筛选**：直方图平坦、没有聚簇的项目直接淘汰，不必构建。

---

## 5. 实测：一次构建服务全部 PoC

在候选基线上构建一次，把该项目**全部 PoC 一起回放**（assimp 实测 26 个 PoC 共 2 秒），
直接得到"这个基线上谁活着"的整个向量。所以成本是 `候选基线数 × 一次构建`，
不是 `漏洞数 × 一次构建`。

`scripts/sweep_probe.sh` 已在 ARVO 容器内跑通，做的就是这件事：
checkout 上游 commit → `compile` → 回放全部 PoC → 输出每个 PoC 的 clean/asan/signal。

取开火数最高的基线作为该项目的目标。开火数并列时取时间较晚的（未知漏洞污染较轻，见 §10）。

## 6. 准入：三条

漏洞 i 进入目标当且仅当：

| # | 闸门 | 判据 |
|---|---|---|
| 1 | **开火** | `poc_i` 在基线二进制上产生 ASan 报告或信号 |
| 2 | **指纹匹配** | 报告指纹匹配 ARVO 参考指纹：`(kind, access, crash_func, crash_file)`，行号允许漂移 |
| 3 | **可区分** | 指纹在本目标内唯一；与其他漏洞相同则合并为一个 ID |

闸门 2 是防 Magma 病的唯一一道，也是必需的一道：崩了不等于崩的是那个漏洞。

不设的闸门及理由：负对照（§2，天然潜伏无此问题）、隔离对照（不追求干扰量测量）、
确定性（关 ASLR + 固定 `ASAN_OPTIONS` 已足够，见 [determinism.md](determinism.md)）。

## 7. 选项目

| 条件 | 阈值 | 来源 |
|---|---|---|
| ARVO 去重崩溃点数 | ≥ 15 | `memvul census` 已产出 |
| fix 日期存在聚簇 | 至少一波 ≥6 个同期修复 | §4 直方图，零成本 |
| harness 执行速度 | 越快越好，直接决定战役成本 | ARVO 镜像实测 |
| 老 commit 可构建 | ARVO 的 `compile` 对目标年份仍适用 | sweep 时自然暴露 |

普查已知：ARVO-Meta v3 的 6138 条里，去重后 ≥10 个崩溃点的 (项目, harness) 组有 **62 个**。
从中挑 12 个绰绰有余，可以按上表严格筛。

**开发节奏**这条老结论在纯考古路线下更重要了：harfbuzz 这类高频项目漏洞窗口中位数只有
27 天，天然共存概率低；assimp / matio 这类节奏慢的项目窗口长。优先低频项目。

**模块化程度**这条则不再是一等条件——它原本是用来预测 pin 冲突率的，没有 pin 就没有冲突。

## 8. 交付与评测

每个目标交付：

```
targets/<project>/
├── target.yaml       基线 commit、harness、漏洞清单
├── Dockerfile        基于 ARVO 镜像，checkout 到基线
├── bugs/<BUGID>/     poc + 参考 ASan 报告 + 指纹
└── replay.sh         回放与归因
```

两个构建变体：

- **eval build**：被测工具实际跑的二进制，标准 ASan 配置，不含任何探针。
- **recover build**：同源同 commit，`-fsanitize-recover=address` + `halt_on_error=0`。
  只在战役结束后离线用——把工具存下的全部输入灌一遍，**补捞被掩蔽的漏洞**
  （一个输入同时踩中 3 号和 7 号时，正常 ASan 只报 3 号）。这一步很便宜，
  但能显著提高可报告的漏洞数。

评测协议的最小可信集：

- **种子集统一，且绝不含任何 PoC 或其变体。** 种子选择是已知的头号混淆因素。
- ≥10 次重复、24h，报 Mann-Whitney U + Vargha-Delaney Â₁₂（Klees et al. 口径）。
- 主指标：发现的不同漏洞数、每漏洞首次发现时间。
- 归因：工具 `crashes/` 里的输入灌进 recover build，按指纹映射到 bug ID；
  归不到任何已知漏洞的崩溃簇单独报出，不计入主指标。

## 9. 可选增量：机会主义 pin

先跑完 §4–§6 拿到全部项目的天然产量数据，**再决定要不要做这一步**。

如果某个目标的天然产量偏低，可以低成本补一层：对基线上没开火的漏洞，
只挑**修复恰好只改一个源文件**（assimp 是 28/34）且该文件没被天然层漏洞碰过的，
把该文件换成 `fix_commit^` 的版本，重建，回放。**成了就收，不成就扔。**

关键简化：pin 到 `fix^` 就**不需要知道存活窗口**——`fix^` 按定义必然是漏洞形态。
原方案里最贵的"存活窗口实测"整块因此消失。同样地：不做认领集扩张、不建冲突图、
不做最大独立集求解。所有候选一次性铺上、构建一次、一起回放。

代价是保真不再平凡满足（需要记录 pin 表），且负对照重新成为必需（要证明是 pin 造成的崩溃）。
所以这一步只在数据表明确实需要时才做。

## 10. 有意放弃的严谨性（记录在案）

写论文时会被问到，所以先记下放弃了什么、代价是什么：

| 放弃的东西 | 代价 | 缓解 |
|---|---|---|
| 单目标高密度（26 → 8） | 单次战役信息量低 | 靠目标数量补，总漏洞数反而更高（§3） |
| 漏洞难度标定 | 主指标是等权计数，一道口算题和一道竞赛题各算一分；若多数漏洞人人秒杀则分辨率不足 | 报每漏洞 TTD 曲线而非只报总数，读者可自行看分布 |
| 密度失真量化 | 无法回答"共驻是否改变了单个漏洞的发现难度" | 密度只有 8，失真幅度本就小于原方案 |
| 未知漏洞普查 | 工具报出的崩溃有一部分归不到已知漏洞，败坏归因分母 | §8 要求单独报出未归因崩溃簇；§5 并列时取较晚基线 |
| 确定性契约 D1–D4 | 无法保证逐字节可重放 | 关 ASLR + 固定 `ASAN_OPTIONS`，对 TTD 统计足够 |
| 语料的选择偏差 | 所有漏洞都是 OSS-Fuzz 用现有 fuzzer 找到过的，难度天花板被封死，测的是速度不是能力边界 | **无解**，写进论文局限性 |

## 11. 两条不能破的规矩

1. **选基线和选漏洞时不看被测工具的表现。** 基线按天然产量选，漏洞按能否复现加指纹是否匹配收，
   全程只用上游属性。这条零成本，但一旦破了，"你的 benchmark 是照着你的方法挑的"一句话就能否掉全部结果。
2. **论文里同时要有 Magma 或 FuzzBench 的结果。** 自建集的定位是补充证据——更多漏洞、更细分辨，
   不是唯一证据。这也是为什么不必把它做到发表级严谨：它不是论文的主张。

## 12. 流水线

| 阶段 | 命令 | 输入 → 输出 | 状态 |
|---|---|---|---|
| 普查 | `memvul census` | ARVO-Meta → 分类与去重崩溃点 | 已有 |
| 候选基线 | `memvul candidates` | fix 日期直方图 → 每项目 ~5 个候选，**零构建** | 待实现（§4） |
| 实测 | `memvul sweep` | 候选基线 → 每基线的开火向量 | `scripts/sweep_probe.sh` 已跑通 |
| 选定 | `memvul base` | 开火向量 → argmax 基线 + 漏洞清单 | 已有，需改为读 sweep 结果 |
| 验证 | `memvul verify` | 三道闸门 → `bug.yaml` | 已有，需简化到三条 |
| 物化 | `memvul emit` | 基线 + 漏洞清单 → 目标镜像与目录 | 已有，需去掉 pin 表 |

`memvul pin` / `memvul slice` 属于 §9 的可选增量，**本轮搁置**，代码保留不删。
